# Проверки файлового транспорта

## Обновление до upstream 1.9.2 — 27.10.2026

Upstream: `v1.9.2`, коммит `46eaa7454292e3e8a8159f631190221b5ffdce72`.
Обновление объединено с RDP-мостом; его протокол и CLI не менялись.
В списке модулей пакета сохранены `_file_bridge` и новый `_keyboard_macos`.

- Повторно прошли 18 тестов файлового транспорта и 12 тестов обёртки ожидания
  в harness.
- Собран wheel 1.9.2. Пройден запуск из отдельной проверочной установки:
  MCP → файлы → worker → штатный MCP → локальная демобаза 1С 8.3.27.2342,
  открытие списка, чтение формы и завершение созданного клиента.
- Локально проверено обновление переносного Python отдельным каталогом
  пакета без изменения зависимостей. Это проверка механизма установки,
  а не подтверждение обновления реального терминала.

RDP worker во время обновления недоступен; применение 1.9.2 и повторная
проверка на клиентском терминале требуют отдельного запуска. Успешные
RDP-проверки ниже относятся к 1.9.1 и не выданы за проверки новой версии.
Новый поиск в списках БСП и клавиши macOS отдельно на реальном UI не проверялись.

## Исходная проверка моста на 1.9.1

Дата: 26.10.2026. Базовая ревизия upstream: 1.9.1,
`e45c31beb2ce1c7b82499eb4fd4e888c799ec3fa`.
Результаты относятся к реализации `_file_bridge.py` и описанным ниже средам,
а не к произвольной установке Testpilot. Здесь нет адресов клиентских серверов,
профилей с паролями и содержимого информационной базы.

## Автоматические проверки в этом форке

```powershell
python -m unittest discover -s tests -v
```

18 тестов в `tests/test_file_bridge.py` проверяют:

- обмен запросом/ответом и освобождение pending после получения;
- истечение срока до исполнения без вызова действия;
- сохранение блокировки неизвестного результата после перезапуска proxy;
- поздний ответ без повторного исполнения;
- падение после захвата: `.running` не исполняется снова;
- изоляцию каналов и нового UUID worker от старой очереди;
- проверку адресации и повреждённых MCP-ответов;
- передачу изображения, `isError` и повторное чтение последнего результата;
- игнорирование временных файлов и отказ для устаревшего heartbeat;
- имена каналов, блокировки worker и конкурирующих proxy;
- повтор только публикации при кратком отказе Windows в замене файла;
- обновление heartbeat без перезаписи схем инструментов.

Автотесты используют временные каталоги и подставной обработчик; 1С и RDP
для них не нужны. Это проверка протокола, а не бизнес-сценариев базы.

Сценарий ожидания и возобновления — обёртка интеграции harness, не новый

интеграции; в публичную документацию включена только эта сводка.

## Выявленные проблемы и границы вывода

- При чтении `current.json` с другой стороны RDP происходил краткий отказ
  Windows в `os.replace`. Добавлены ограниченный повтор публикации тех же
  байтов и отдельный heartbeat; действия 1С при этом не повторяются.
- Раннее чтение активного окна во время загрузки приводило к отсутствию окна
  или тайм-ауту тестового протокола. Проверка отделяет подключение от готовности
  UI и ищет главное окно среди окон приложения; вторичная стартовая форма не
  считается неудачным запуском.
- Один ранний запуск показал пользователю прикладную ошибку 1С. Её текст не
  был получен, причина не установлена; успешный позднейший прогон не является
  диагнозом этой ошибки.
- Файловая демобаза на терминале не получила лицензию; RDP UI проверялся на
  серверной тестовой копии, а не на этой файловой базе.

Не подтверждены этой проверкой: разрыв реального RDP во время изменяющего
действия, длительная нагрузка, другие терминальные среды, Linux/macOS,
бизнес-сценарии с записью документов и фактическое сравнение прав нескольких
пользователей. Часть отказов покрыта моделируемыми тестами, что не заменяет
испытание конкретной среды. Сам мост сохраняет права и ограничения штатного
Testpilot и пользователя 1С.

## Минимальная приёмка в новой среде

1. Проверить доступность общей папки с двух сторон и запустить один worker.
2. Через proxy получить `online=true`, `pending=null` и список профилей.
3. На тестовой базе запустить один клиент либо выбрать уже существующий.
4. Дождаться главного окна и прочитать текущий командный интерфейс без
   переключения разделов.
5. Сохранить результат, версию платформы и идентификаторы подключения/worker.
6. Закрыть только созданный тестом клиент, если это входит в сценарий,
   и проверить отсутствие pending.

При ошибке использовать [порядок восстановления](FILE_BRIDGE.md#диагностика-и-восстановление).
Тайм-аут не даёт основания повторять изменяющую команду.
