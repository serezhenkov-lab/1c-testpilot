# Установка файлового моста Testpilot

Инструкция относится к исходникам этого форка с модулем `app/_file_bridge.py`.
Примеры используют условную базу `test-server\test-copy`, канал `test-copy`
и каталог `C:\1C-Bridge`. Замените их своими значениями. Установка не требует
размещения исходников в конкретном проекте или использования harness.

## 1. Подготовить две среды

На компьютере разработчика нужны Python с зависимостями Testpilot и MCP-клиент
с поддержкой stdio. На терминале нужны:

- Python с тем же пакетом форка и его зависимостями;
- интерактивный сеанс Windows с установленным клиентом 1С;
- доступ к тестовой информационной базе и подходящая лицензия 1С;
- возможность создавать файлы, запускать дочерний процесс и соединяться
  с клиентом тестирования по loopback;
- доступ к одной общей папке с двух сторон RDP.

Пакет декларирует Python 3.10+. Реальная проверка моста выполнена на Python
3.14.6 x64; другие версии требуют проверки своей среды. Версии платформы
приведены в [протоколе проверок](FILE_BRIDGE_VALIDATION.md).

Из корня локального checkout форка на каждой стороне, где установлен Python:

```powershell
python -m venv .venv
& '.\.venv\Scripts\python.exe' -m pip install .
& '.\.venv\Scripts\python.exe' -m _file_bridge --help
```

Не заменяйте работающий runtime во время теста. Для обновления закончите
операции, выясните исход всех `pending`, остановите worker и установите
проверенную ревизию. Исходники и каталоги обмена храните раздельно.

Если Python на терминале устанавливать нельзя, допустим заранее подготовленный
переносной runtime с зависимостями. Такой вариант проверен на Windows x64.
Этот репозиторий не содержит готового portable-архива или универсального
установщика Python: комплект нужно подготовить отдельно под ОС/архитектуру,
перенести на терминал и проверить там `python.exe -m _file_bridge --help`.
Копирование одного `python.exe` недостаточно; нужны стандартная библиотека,
пакеты и бинарные зависимости, включая pywin32. Копия обычного venv между
машинами также не является переносным дистрибутивом.

## 2. Подготовить папку обмена

На компьютере разработчика создайте каталог вне Git-репозитория:

```powershell
New-Item -ItemType Directory -Force 'C:\1C-Bridge' | Out-Null
```

Разрешите перенаправление нужного диска в настройках RDP-подключения. Внутри
терминала проверьте `\\tsclient\C\1C-Bridge` через Проводник или PowerShell:

```powershell
Test-Path -LiteralPath '\\tsclient\C\1C-Bridge'
```

Локальный `C:\1C-Bridge` и удалённый `\\tsclient\C\1C-Bridge` должны указывать
на **одни и те же файлы**. Диск `C:` самого терминального сервера — другой диск.
1С:Предприятие на сервере базы не обязано видеть `\\tsclient`: файлы читает
Python worker в пользовательском RDP-сеансе.

Не давайте посторонним доступ к каталогу: файлы запросов содержат исполняемые
команды, а ответы могут содержать данные базы. Правила именования каналов:
1–64 символа ASCII, первая буква/цифра, далее буквы, цифры, `_` и `-`;
имена устройств Windows исключены. Регистр приводится к нижнему.

## 3. Настроить профили на терминале

Сохраните UTF-8 YAML, например `C:\Testpilot\profiles.yaml`, **локально на
терминале**, вне общей папки и Git. JSON с такой же структурой тоже допустим.
Пример для ручного входа и входа двух разных пользователей:

```yaml
profiles:
  test-manual:
    base: 'test-server\test-copy'
    server: true
    version: '8.3.27.1989'
    wait: 240
  test-manager:
    base: 'test-server\test-copy'
    server: true
    version: '8.3.27.1989'
    user: 'TestManager'
    password_env: TESTPILOT_MANAGER_PASSWORD
    wait: 240
  test-accountant:
    base: 'test-server\test-copy'
    server: true
    version: '8.3.27.1989'
    user: 'TestAccountant'
    password_env: TESTPILOT_ACCOUNTANT_PASSWORD
    wait: 240
```

Укажите реально установленную версию либо `exe` с полным путём к `1cv8c.exe`.
Переменные `password_env` должны существовать в окружении worker на терминале
**до его запуска**. Менять их в другом PowerShell после старта worker
недостаточно. Для ручного ввода пароля переменные не нужны.

Альтернатива `password_env` — поле `password` в локальном профиле. Это открытый
текст, поэтому ограничьте доступ к файлу. Одновременно оба поля недопустимы.
При запуске 1С пароль попадает в командную строку её процесса при обоих способах;
профили не являются хранилищем секретов с шифрованием.

`list_profiles` не возвращает пароль. При `launch_client(profile=...)` в
файловый запрос попадает имя профиля; если же явно передать `password` в MCP,
он сохранится в запросе. Файл профилей перечитывается при обращении: добавление
профиля не требует перезапуска worker. Права в базе определяются пользователем
1С, а не именем профиля; для сравнения прав запускайте отдельные подключения.

## 4. Запустить worker на терминале

Пример для установленного в `C:\Testpilot` runtime (путь адаптируйте):

```powershell
$env:TC1C_RESPONSE_FORMAT = 'json'
$env:TC1C_RESPONSE_DETAIL = 'full'
& 'C:\Testpilot\.venv\Scripts\python.exe' -m _file_bridge worker --root '\\tsclient\C\1C-Bridge' --channel test-copy --profiles 'C:\Testpilot\profiles.yaml'
```

Дождитесь `Worker ready: channel=test-copy session=...`. Оставьте консоль
работать. Сам worker не запускает базу до команды MCP. Для одной папки канала
разрешён один worker; для разных каналов нужны отдельные процессы.

Если настройки основного Testpilot хранятся в `.env`, worker поддерживает
`--env-file <путь-на-терминале>`. Внутреннее соединение с дочерним MCP всегда
использует stdio независимо от HTTP-настроек окружения.

## 5. Подключить proxy к MCP-клиенту

Пример секции конфигурации Codex на компьютере разработчика:

```toml
[mcp_servers."1c-testpilot-rdp"]
command = 'C:\Testpilot\.venv\Scripts\python.exe'
args = ['-m', '_file_bridge', 'proxy', '--root', 'C:\1C-Bridge', '--channel', 'test-copy', '--timeout', '300']
tool_timeout_sec = 360
```

Для другого MCP-клиента перенесите те же `command` и `args` в его stdio-конфиг.
Python и модуль берутся с локального компьютера, root — локальное представление
общей папки. Не запускайте второй proxy для параллельного управления тем же
каналом. Отдельный обычный MCP Testpilot можно сохранить под другим именем.

Запуск proxy вручную не открывает интерактивный интерфейс: процесс ожидает MCP
JSON-RPC по stdin. Сначала запустите worker, затем подключите MCP-клиент;
если worker появился позже, перечитайте список tools или переподключите proxy.

## 6. Проверить канал и прочитать интерфейс

Вызовите через **RDP MCP**, последовательно:

1. `tp_bridge_status {}` — ожидаются `online=true`, `pending=null`.
2. `tc_session {"action":"list_profiles"}` — убедитесь, что выбран нужный профиль.
3. `tc_session {"action":"list_connections"}` — используйте уже открытый
   подходящий клиент, если он есть.
4. Для нового клиента:
   `tc_session {"action":"launch_client","profile":"test-manual","connect":false}`.
   Сохраните возвращённые `connection_id`, `port`, `version`.
5. Завершите ручной вход, если появился запрос, затем выполните `connect`:

```json
{"action":"connect","connection_id":"<id из запуска>","host":"127.0.0.1","port":15431,"version":"8.3.27.1989"}
```

`15431` и версия в примере условные: подставьте **значения из своего ответа**.
Порт относится к терминалу, `127.0.0.1` не означает компьютер разработчика.

Дождитесь главного окна по алгоритму
[ожидания готовности](FILE_BRIDGE.md#ожидание-готовности-1с). Чтение
`get_child_objects(scope="application")` и
`get_command_interface(ref=<ref главного окна>, all_sections=false)` не
переключает разделы. Успех запуска по TCP-порту сам по себе не подтверждает
готовность UI. При нескольких клиентах передавайте `connection_id` во всех
вызовах; `ref` берите только из текущего ответа выбранного клиента.

После проверки оставьте клиент открытым либо явно вызовите
`tc_session(action="stop_client", connection_id=...)` только для клиента,
который создал ваш тест. У `stop_client` возможна принудительная остановка
после истечения ожидания штатного выхода; несохранённая работа может потеряться.

## 7. Завершение и обслуживание

Закончите текущие действия и проверьте отсутствие неизвестного результата.
Остановка worker через Ctrl+C завершает дочерний MCP и может закрыть созданные
им тестовые клиенты. Повторный запуск worker создаёт новый UUID сеанса;
старые запросы не переносятся и не исполняются заново.

При обновлении или архивировании каталога обмена сначала завершите оба
компонента. Результаты не удаляются автоматически: храните нужные доказательства
проверок, а устаревшие каталоги архивируйте по принятому сроку хранения.
Не удаляйте `pending.json`, чтобы просто снять ошибку: сначала выясните исход
операции по [порядку восстановления](FILE_BRIDGE.md#диагностика-и-восстановление).
