# Файловый транспорт через RDP

Экспериментальное дополнение форка. Обычные `1c-testpilot`, MCP и Python API
не меняются. Новый CLI: `1c-testpilot-file` (или `python -m _file_bridge`).

Пошаговое развёртывание: [установка и первый запуск](FILE_BRIDGE_SETUP.md).
Результаты: [проверки и ограничения](FILE_BRIDGE_VALIDATION.md).
Реализация: [`app/_file_bridge.py`](../app/_file_bridge.py), тесты:
[`tests/test_file_bridge.py`](../tests/test_file_bridge.py).

```text
MCP-клиент -> локальный proxy -> файлы общего каталога
                                 -> worker на терминале -> штатный MCP Testpilot
                                                           -> 1С /TESTCLIENT
```

Worker держит один дочерний stdio MCP-сервер Testpilot и сохраняет его состояние
между вызовами. Передаются имена инструментов, аргументы и полные CallToolResult,
включая ошибки, structuredContent и изображения. Схемы инструментов приходят
от сервера на терминале; копия схем вручную не поддерживается.

## Запуск

На обоих компьютерах нужны Python и пакет с зависимостями. На терминале можно
использовать заранее подготовленный переносной комплект. Интерпретатор worker
должен уметь `python -m _cli` (штатный сервер Testpilot).

На терминале, в интерактивном сеансе пользователя:

```powershell
python -m _file_bridge worker --root '\\tsclient\C\1C-Bridge' --channel client-test
```

Для Testpilot допустим `--env-file` с настройками на терминале. Профили баз,
пути к платформе, EPF, отчётам и другим файлам относятся к терминалу.
Пароли лучше хранить в настройках профиля на терминале, а не передавать в
аргументах MCP: файлы запросов сохраняются для диагностики.

`--profiles <путь>` задаёт YAML/JSON-файл штатных профилей Testpilot на терминале.
Можно хранить несколько профилей одной базы для разных пользователей/ролей.
`tc_session(action="list_profiles")` возвращает имена профилей без паролей;
`tc_session(action="launch_client", profile="catest-manager")` выбирает профиль.
Пароль не передаётся через файловый канал при таком запуске. Файл перечитывается
при обращении, поэтому изменение профилей не требует перезапуска worker.
Обычные поля `user`, `password`, `password_env` поддерживаются upstream; пароль
в профиле хранится открытым текстом и при запуске 1С попадает в командную строку
процесса. Не добавляйте файл профилей в Git или общий каталог обмена.

После сообщения `Worker ready` запустить локальный MCP по stdio:

```powershell
python -m _file_bridge proxy --root 'C:\1C-Bridge' --channel client-test --timeout 300
```

Один канал — один worker и одна последовательность действий. Разные каналы
используют разные каталоги и независимые worker. Конкурирующий proxy получает
ошибку busy; новые команды не накапливаются за выполняющейся операцией.
Для обычной работы запускайте один MCP proxy на канал.

### Параметры CLI

| Параметр | Где используется | Назначение |
| --- | --- | --- |
| `proxy` / `worker` | Обязательный режим | Локальный stdio MCP либо исполнитель на терминале |
| `--root` | Оба режима, обязателен | Корень обмена; пути разные, физические файлы общие |
| `--channel` | Оба режима, обязателен | Имя из 1–64 символов ASCII; первая буква/цифра, далее также `_` и `-`; приводится к нижнему регистру, имена устройств Windows запрещены |
| `--timeout` | Proxy | Положительное конечное число секунд, по умолчанию 120; одновременно срок запроса и ожидание ответа; рекомендуемый старт для медленного RDP — 300 |
| `--env-file` | Worker | Путь к настройкам штатного Testpilot на терминале |
| `--profiles` | Worker | Путь к YAML/JSON профилям на терминале; задаёт `TC1C_PROFILES_FILE` дочернего MCP |

`--timeout` не ограничивает время уже исполняемого действия на терминале.
Отдельный внутренний тайм-аут MCP worker составляет один час. Параметры
прокси не перенастраивают тайм-аут тестового протокола 1С.

### Границы ответственности

- `Proxy` публикует запрос и хранит его незавершённое состояние между
  перезапусками локального MCP. Он не соединяется с 1С по TCP.
- `Worker` владеет дочерним `python -m _cli`, обеспечивает последовательную
  обработку и передаёт ему параметры tools без изменения их семантики.
- Штатный MCP Testpilot хранит подключения, запускает клиент 1С, проверяет
  доступность действий и возвращает результат. Правила доступа не обходятся.
- Клиент 1С работает в RDP-сеансе. Прямое подключение по тестовому протоколу
  остаётся локальным для терминала; отдельное расширение конфигурации ради
  самого файлового транспорта не требуется.

## Протокол и восстановление

### Ожидание готовности 1С

Открытый TCP-порт и успешный `connect` ещё не означают, что база загрузила
главное окно. Для медленной базы или ручного ввода пароля разделяйте запуск
и чтение UI:

1. `tc_session(action="list_connections")`: выберите существующий клиент,
   если он уже открыт. Не повторяйте `launch_client` после тайм-аута.
2. Если клиента нет, один раз вызовите
   `tc_session(action="launch_client", profile="...", connect=false)`.
   Сохраните `connection_id`, `port` и `version` из ответа.
3. После начальной загрузки вызовите `tc_session(action="connect", ...)`
   с этим `connection_id`, портом и версией платформы.
4. На время проверки увеличьте `tc_app(action="set_max_action_time",
   seconds=120, connection_id="...")`: стандартное ожидание ответа — 30 секунд.
   Тайм-аут файлового proxy должен быть больше времени отдельного вызова.
5. Читайте `tc_app(action="get_child_objects", scope="application", ...)`,
   ищите `is_main=true` / `class="MainFrame"`. Стартовая вторичная форма
   может быть активной и не является признаком неудачного запуска.
6. При успешном ответе без главного окна допустим следующий опрос после паузы,
   в пределах общего бюджета ожидания. Ошибка MCP или тайм-аут протокола —
   повод остановить сценарий и проверить состояние, а не повторять запуск.

При чтении меню используйте возвращённый `ref` главного окна и
`tc_window(action="get_command_interface", all_sections=false, ...)`.
После проверки восстановите прежний тайм-аут; закрывайте только клиент,
созданный данным сценарием, если такое закрытие запрошено. Клиент после
ошибки оставляйте для диагностики. Это порядок работы со штатными tools;
транспорт не меняет поведение `launch_client` и не добавляет скрытых повторов.

### Файлы канала

```text
<root>/<channel>/
  worker.lock
  proxy.lock
  current.json
  heartbeat.json
  pending.json                # только пока исход запроса не получен
  last-result.json
  <worker-session-uuid>/
    <request-uuid>.request.json
    <request-uuid>.running     # запрос после захвата; сохраняется и после ответа
    <request-uuid>.response.json
```

UUID сеанса и запроса — 32 шестнадцатеричных символа без дефисов. Версия
протокола `protocol=1`. Общая адресация — `channel`, `session`, а для запросов
и ответов также `request`. Worker проверяет канал и UUID своего сеанса,
proxy проверяет всю адресацию ответа перед принятием результата.

Пример запроса (идентификаторы и время условные):

```json
{
  "protocol": 1,
  "channel": "test-copy",
  "session": "11111111111111111111111111111111",
  "request": "22222222222222222222222222222222",
  "tool": "tc_session",
  "created": 1793000000,
  "expires": 1793000300,
  "arguments": {"action": "list_connections"}
}
```

`pending.json` содержит ту же адресацию, tool и времена, но без `arguments`.
Ответ содержит адресацию и поле `result` — стандартный MCP `CallToolResult`:
`content`, необязательный `structuredContent`, флаг `isError`. Сам транспорт
не превращает ошибку tool в успешный результат.

- `current.json`: версия протокола, канал, UUID сеанса и схемы tools.
  Отдельный маленький `heartbeat.json` обновляется каждые 5 секунд; proxy
  требует возраст до 30 секунд. Схемы переписываются только при изменении.
  Часы компьютеров должны быть синхронизированы. Это проверка доступности,
  а не гарантия успешного выполнения следующего действия.
- `worker.lock` и `proxy.lock`: системные блокировки байта файла. При завершении
  процесса ОС освобождает блокировку; второй worker не должен работать в канале.
  Поддержку блокировок конкретным перенаправлением RDP нужно проверять.
- `<session>/<request>.request.json` публикуется через временный файл и rename.
  До публикации proxy записывает `pending.json`; при любой неопределённости
  канал остаётся заблокирован. Максимальный размер JSON — 32 МиБ.
- Worker переименовывает запрос в `.running` перед исполнением, проверяет
  UUID/канал/срок. Просроченный запрос не исполняется. `.running` никогда не
  подхватывается повторно, даже после сбоя. После перезапуска worker создаёт
  новый UUID и не просматривает старые очереди.
- Ответ публикуется атомарно. Proxy валидирует адресацию и CallToolResult,
  сохраняет `last-result.json`, затем снимает pending. Сами запросы и ответы
  не удаляются автоматически. Частичные `.tmp` игнорируются.
  При кратком отказе Windows/RDP в замене файла повторяется только rename
  готового файла (до 5 секунд), но никогда не исполнение команды 1С.
- Тайм-аут proxy НЕ отменяет действие в 1С. Повтор действия запрещён до
  выяснения исхода. `tp_bridge_status` показывает request id и наличие ответа;
  `tp_bridge_result(request=...)` получает поздний ответ без повторного исполнения.
  Последний уже полученный ответ также можно прочитать по id.
- Если ответ потерян окончательно, автоматического снятия блокировки нет.
  Оператор проверяет исход в 1С и останавливает оба компонента; только после
  этого может архивировать `pending.json` для восстановления канала. Не переносите
  старые запросы в новый UUID. Это не exactly-once транзакция с информационной базой.
- Исключение транспорта worker после отправки MCP-команды оставляет `.running`
  и прекращает работу worker: результат неизвестен. Ограничение ожидания
  внутреннего MCP-вызова — один час; timeout proxy настраивается отдельно.

### Состояния одного запроса

```text
нет pending
  → pending записан
  → .request.json опубликован
  → .request.json переименован в .running
  → действие выполнено, .response.json опубликован
  → proxy проверил ответ и записал last-result.json
  → pending удалён
```

Любая ошибка после записи `pending` оставляет канал закрытым для новых
действий. Падение после захвата, но до исполнения неотличимо от падения после
исполнения без ответа: оба случая требуют разбирательства, а не повтора.
Это сознательный выбор в пользу отсутствия автоматического дублирования;
гарантии доставки, транзакционности или exactly-once для 1С здесь нет.

Файлы JSON сначала записываются во временный файл с `fsync`, затем публикуются
через `os.replace`. На Windows краткий `PermissionError` при замене повторяет
только публикацию тех же байтов до пяти секунд. Блокировки используют
`msvcrt.locking` на Windows и `flock` на POSIX. Работоспособность блокировок
и переименования зависит от файловой системы и конкретного перенаправления.

### Служебные MCP-инструменты

`tp_bridge_status {}` читает локальные метаданные без отправки команды worker.
Возвращает `channel`, `online`, при доступности `session`, `pending`,
`response_available`, `last_request`; при недоступности — также `error`.
`online=true` означает свежий heartbeat, но не готовность базы или интерфейса.

`tp_bridge_result {"request":"<id>"}` возвращает исходный MCP-результат
позднего ответа и снимает соответствующий pending. Когда ответ уже доставлен,
можно повторно получить **последний** результат из `last-result.json`.
Произвольный исторический результат инструмент не ищет. Несовпадение UUID,
повреждённый ответ и отсутствие ответа оставляют pending без изменений.

## Диагностика и восстановление

| Симптом | Проверка и действие |
| --- | --- |
| Нет `Worker ready` | Проверить локальный Python, зависимости, доступ к общей папке, путь к профилям и журнал worker |
| `Worker offline/stale` | Проверить RDP-сеанс, доступность диска, heartbeat, синхронизацию часов; команды ещё не отправлены |
| `Channel is busy` | Проверить второй worker/proxy или текущий запрос; не удалять lock-файл работающего процесса |
| `Unresolved request` / `Timeout; outcome unknown` | Прочитать `tp_bridge_status`, сохранить request id; при `response_available=true` вызвать `tp_bridge_result` |
| Ответ пока не появился | Дождаться результата и читать статус; не повторять бизнес-действие и не запускать второй клиент вместо первого |
| `Request expired before execution` | Worker захватил просроченный запрос и вернул ошибку без его исполнения; сверить настройки времени и задержки |
| `Session mismatch` / `Request mismatch` | Сохранить диагностические файлы; не переносить запросы/ответы между UUID и не редактировать адресацию |
| `PermissionError` при RDP I/O | Краткое препятствие публикации обрабатывается кодом; постоянную ошибку диагностировать по доступности/правам папки; проверить pending до следующего действия |
| Ошибка `tc_app: timed out` | Файловый ответ получен, но тестовый протокол 1С не ответил вовремя; проверить окно базы и готовность клиента, не считать действие отменённым |
| Пустой интерфейс после запуска | Проверить ручной вход, лицензию, стартовые диалоги и версии; TCP-порт не является признаком готовности приложения |

Если ответа окончательно нет: зафиксируйте файлы и состояние 1С, выясните
результат действия, остановите оба компонента и убедитесь, что они больше не
исполняют запрос. Только после этого оператор может архивировать pending и
сеанс для нового канала/сеанса. Не переименовывайте `.running` обратно в
`.request.json`, не копируйте его в новый сеанс. Автоматического «сброса» или
повтора неизвестного действия транспорт намеренно не предоставляет.

Окно лицензирования, пароль 1С и сообщения прикладной конфигурации требуют
отдельного решения. Увеличение тайм-аута не исправляет ошибку входа или лицензии.

## Ограничения

Публикуются tools; проксирование MCP resources/prompts и подписок не реализовано.
Динамические схемы обновляются после вызова на worker, но автоматические
уведомления tools/list_changed через файловый слой не передаются: перечитайте
инструменты/переподключите MCP после изменения их состава.
Возвращённый путь к файлу на терминале не делает файл доступным локально;
через мост передаётся только содержимое MCP-ответа, включая inline images.
Метрики, фильтры безопасности и права штатного Testpilot не расширяются мостом.

Ctrl+C останавливает worker и его дочерний сервер. Штатное завершение сервера
может закрыть запущенные им тестовые клиенты; не используйте их для ручной
несохранённой работы. Разрыв RDP-диска может остановить worker; соединение
с интерфейсом и адреса элементов после перезапуска следует получать заново.

Каталог обмена содержит исполняемые задания и ответы базы. Доступ к нему
должен быть только у доверенных пользователей. Аутентификация обеспечивается
правами файловой системы и RDP; встроенного шифрования/анонимизации нет.

## Проверки

```powershell
python -m unittest discover -s tests -v
```

Проверяются тайм-ауты, поздние ответы, блокировки, смена сеанса, изоляция каналов,
повреждённые ответы, истечение срока, изображения и запрет повторного выполнения.
Интеграционные сценарии с реальной 1С и результаты конкретного RDP-сеанса
хранятся отдельно в harness. Обезличенная сводка результатов и точные границы
проверки доступны в [FILE_BRIDGE_VALIDATION.md](FILE_BRIDGE_VALIDATION.md).
